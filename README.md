# Точки — прототип мультиплеера (шаги 1–9)

## Что здесь есть

- `gameEngine.js` — чистые правила игры (без DOM/canvas), общие для клиента
  и сервера. Дебютная зона, захваты, настраиваемые условия окончания, бот —
  всё то же самое, что в однопользовательской версии, но вынесено в
  `createMatch()`, поэтому сервер может держать много независимых партий
  одновременно (по одной на комнату).
- `server.js` — Node.js + WebSocket сервер, авторитетный по состоянию партии.
  - **Комнаты по коду** (шаг 3): один игрок создаёт комнату — сервер выдаёт
    короткий код (5 символов, без похожих друг на друга букв/цифр), второй
    игрок присоединяется по этому коду.
  - **Матчмейкинг** (шаг 4): вместо кода — очередь ожидания. Игрок жмёт
    «Искать соперника», сервер сам сводит его с первым же ожидающим, у
    которого те же настройки партии (размер поля, правила окончания) —
    технически это тот же `createRoom()`, просто код никому диктовать не
    нужно. Если настройки не совпадают, игроки просто ждут каждый в своей
    очереди, пока не найдётся подходящий соперник или поиск не отменят.
  - Сервер сам проверяет каждый ход (чья очередь, легальна ли клетка,
    дебютная зона) и рассылает результат обоим игрокам.
  - **Переподключение** (шаг 5): при создании/входе/подборе сервер выдаёт
    клиенту токен переподключения (клиент хранит его в localStorage). Если
    связь обрывается, место не освобождается сразу — у игрока есть
    `reconnectGraceMs` (по умолчанию 2 минуты) на возврат тем же токеном.
    Браузерный клиент делает это автоматически: при обрыве WebSocket сам
    переподключается (до 20 попыток раз в 1.5 сек) и, если найдёт
    сохранённый токен, тут же восстанавливает партию — без перезагрузки
    страницы. Если игрок так и не вернулся — место освобождается
    окончательно, токен аннулируется, соперник получает об этом уведомление.
  - Пустые комнаты (оба игрока по-настоящему ушли, а не просто временно
    отвалились) автоматически удаляются через `emptyRoomTtlMs` (по
    умолчанию 10 минут).
  - **Бот на уровне комнаты** (шаг 6): при создании комнаты можно включить
    «Играть с ботом» — тогда место 2 сразу и навсегда занимает бот (через
    `match.botMove()` из gameEngine.js — тот же движок, что считал ходы
    бота в однопользовательской версии), партия начинается сразу, без
    ожидания второго человека. Такая комната не принимает вход по коду
    (место 2 уже занято) и не участвует в матчмейкинге. После каждого хода
    человека сервер сам, с небольшой задержкой (~30 мс, чтобы сначала
    доставить ответ на ход человека), считает и применяет ход бота и
    рассылает результат — отдельный клиент для бота не нужен.
- `db.js` / `auth.js` — **регистрация и вход** (шаг 7): SQLite-файл
  (`better-sqlite3`, один файл на диске, путь настраивается через
  `DB_PATH`, по умолчанию `./data/tochki.db`). Учётная запись — ник,
  почта, пароль; **ник и почта уникальны без учёта регистра** (проверка
  на уровне приложения, а не через `COLLATE NOCASE`, — встроенная
  коллация SQLite умеет только ASCII A-Z и не годится для кириллицы).
  Пароли хранятся только как `scrypt`-хэш со своей солью на каждый
  пароль, в открытом виде — никогда. HTTP JSON API поверх того же
  сервера:
  - `POST /api/register {nickname, email, password}` → `201 {user, token}`
    или `409 {error, field}` (`nickname-taken` / `email-taken` /
    `invalid-nickname` / `invalid-email` / `invalid-password`)
  - `POST /api/login {login, password}` (`login` — ник или почта) →
    `200 {user, token}` или `401 {error:'invalid-credentials'}` — причина
    отказа одна и та же и для «нет такого пользователя», и для «неверный
    пароль», чтобы нельзя было перебором узнать, какие ники/почты заняты
  - `GET /api/me` с заголовком `Authorization: Bearer <token>` →
    `200 {user}` или `401`
  - `POST /api/logout` с тем же заголовком → аннулирует токен сессии
  - Это самостоятельный слой поверх существующей сетевой части: партии
    по-прежнему можно создавать и без входа (комнаты/коды/токены
    переподключения с учёткой не связаны) — `client.html` просто
    добавляет форму входа/регистрации сверху лобби.
  - Комнаты партий по-прежнему живут в памяти процесса, как и раньше —
    БД сейчас only для учётных записей, не для активных партий (см.
    «Что дальше»).
- **Ник вместо «Индиго»/«Гранат» (шаг 8):** если игрок вошёл в учётную
  запись, WS-сообщения `create-room` / `join-room` / `find-match` /
  `reconnect` несут необязательное поле `authToken` (токен сессии из
  `/api/login` — не путать с `token` переподключения к месту, который
  выдаёт сама комната). Сервер резолвит его в ник и кладёт в
  `room.playerNames: {1, 2}` — это поле рассылается в `room-created`,
  `room-joined`, `match-found`, `reconnected` и каждом `state`, так что
  **и владелец, и оппонент видят настоящий ник друг друга**, а не то, что
  клиент мог бы придумать сам. Не вошедшие игроки получают `null` —
  клиент сам подставляет запасное имя («Индиго»/«Гранат»); бот получает
  имя вида «Бот (обычный)»/«Бот (сильный)» сразу при создании комнаты.
  Проверено в `test/names.js`: и создатель, и присоединившийся видят
  правильные ники по обе стороны, гость остаётся `null`, имя бота
  подставляется.
- `db.js` / `gamelog.js` — **логи партий и статистика** (шаг 9): каждая
  партия и каждый реально применённый ход (человека и бота) пишутся в БД
  по ходу дела, а не задним числом — таблица `games` (одна строка на
  партию: правила, оба игрока, статус, итог) и `moves` (одна строка на
  каждый ход: координаты, число захваченных камней, счёт сразу после
  хода). Статистика не хранится отдельным счётчиком (который рано или
  поздно разъедется с реальностью), а **пересчитывается SQL-агрегатом**
  по `games` при каждом запросе — источник правды один.
  - Партия попадает в БД сразу при создании комнаты (`status:'in_progress'`),
    имена/id обоих игроков фиксируются **на момент завершения партии** (а
    не создания) — так в логе остаётся ник, под которым доиграли до конца,
    даже если игрок успел перелогиниться между ходами через `reconnect`.
  - `status`: `'finished'` — доиграна (по правилу или кнопкой «Закончить
    игру», см. `end_reason: 'rule'|'manual'`); `'abandoned'` — комнату
    удалили по таймауту недоигранной, никто не вернулся. **Заброшенные
    партии не входят в статистику побед/поражений**, только в общий лог.
  - `GET /api/games/:code` → `{game, moves}` — сводка + полный список
    ходов по коду комнаты (открытый эндпоинт — код и так уже был известен
    обоим игрокам).
  - `GET /api/stats/me` / `GET /api/stats/me/games?limit=20` → своя
    статистика/история партий, нужен `Authorization: Bearer <token>`.
  - `GET /api/stats/:nickname` → публичная статистика любого игрока по
    нику, без входа (только агрегаты, без почты) — например, посмотреть,
    как играет соперник.
  - `stats = {gamesPlayed, wins, losses, draws, gamesVsBot, winRate}`.
  - Проверено в `test/gamelog.js`: ходы (в т.ч. бота) действительно
    попадают в БД с верными координатами/счётом, партия против бота
    доигрывается и фиксируется с `end_reason:'rule'`, заброшенная партия
    помечается `abandoned` и не портит статистику, публичная и приватная
    статистика совпадают, история партий отдаётся без заброшенных.
- `public/client.html` — минимальный браузерный клиент для ручной проверки:
  экран лобби (создать комнату с настройками, опционально с ботом / войти
  по коду / быстрый поиск соперника) + игровой канвас + автоматическое
  переподключение и кнопка «Покинуть комнату». Не финальный дизайн —
  рабочий прототип для проверки сетевой части.
- `test/e2e.js` — автоматический тест: создание комнаты, вход по коду,
  отказ по неверному и по уже занятому коду, очерёдность ходов, дебютная
  зона, синхронность состояния у обоих клиентов, досрочное завершение
  партии, матчмейкинг (очередь, отказ повторному поиску, сведение пары,
  разные настройки не сводятся, отмена поиска), переподключение (временный
  обрыв не путают с уходом, возврат тем же токеном, неверный/просроченный
  токен отклоняется), и игра с ботом — место 2 сразу занято и недоступно
  другому человеку, бот сам отвечает на ход человека без участия второго
  клиента.
- `test/auth.js` — автоматический тест регистрации/входа: успешная
  регистрация, отказ по занятому нику и по занятой почте (в т.ч. при
  другом регистре букв, включая кириллицу), отказ по некорректному
  формату почты и слишком короткому паролю, вход по нику и по почте,
  отказ по неверному паролю, /api/me по токену сессии, аннулирование
  токена по /api/logout. Использует `dbPath: ':memory:'` — ничего не
  остаётся на диске.
- `test/names.js` — автоматический тест того, что ник из учётной записи
  доходит и до владельца, и до оппонента (в `room-created`/`room-joined`/
  `state`), что гость без входа получает `null` (сервер не выдумывает имя
  за него), и что комната с ботом сразу получает читаемое имя бота.
- `test/gamelog.js` — автоматический тест логов партий и статистики (шаг
  9): ходы (человека и бота) пишутся в `moves` с верными данными, партия
  фиксируется в `games` с правильным `end_reason` (по правилу / вручную),
  недоигранная брошенная партия помечается `abandoned` и не искажает
  статистику, `/api/stats/me`, публичная `/api/stats/:nickname` и
  `/api/stats/me/games` отдают согласованные данные.

## Известное ограничение прототипа

Расчёт хода бота (`match.botMove()`) — синхронный и блокирует event loop
Node на время поиска (до `timeLimit` из `DIFFICULTY` в gameEngine.js: ~220 мс
на обычном уровне, ~550 мс на сильном). Для одной-двух комнат с ботом это
незаметно, но при реальной нагрузке с множеством одновременных комнат
стоит вынести расчёт в `worker_threads`, чтобы бот в одной комнате не
подвешивал ходы во всех остальных.

## Протокол (JSON-сообщения по WebSocket)

Клиент → сервер:
```
{type:'create-room', options:{sizeKey, targetScore, targetFillPercent, vsBot, botDifficulty}}
{type:'join-room', code}
{type:'find-match', options:{sizeKey, targetScore, targetFillPercent}}
{type:'cancel-find'}
{type:'reconnect', code, seat, token}
{type:'move', x, y}
{type:'end'}
```

Сервер → клиент:
```
{type:'room-created', code, seat, token, snapshot, vsBot}  — только создателю
{type:'room-joined',  code, seat, token, snapshot}         — только присоединившемуся
{type:'searching'}                             — встал в очередь
{type:'search-cancelled'}                      — вышел из очереди
{type:'match-found', code, seat, token, snapshot}   — обоим сведённым игрокам
{type:'reconnected', code, seat, token, snapshot, vsBot}   — успешно вернувшемуся
{type:'state', snapshot, lastMove?, note?}      — рассылается обоим игрокам
{type:'opponent-disconnected', seat, graceMs}   — оппонент отвалился, ждём возврата
{type:'opponent-left', seat}                    — оппонент не вернулся — место освобождено
{type:'error', reason}
```

## Запуск

```bash
npm install
npm start           # сервер на http://localhost:8080 (или PORT=... npm start)
```

При первом запуске рядом создастся `data/tochki.db` (файл SQLite с
учётными записями) — путь можно переопределить переменной `DB_PATH`.
Файл в `.gitignore`, в репозиторий не попадает.

Откройте `http://localhost:8080` в двух вкладках/окнах браузера (или на двух
устройствах в одной сети, заменив localhost на IP машины с сервером):

**Вариант А — по коду (для конкретного человека):**
1. В первой вкладке — «Создать комнату», задать настройки, получить код.
2. Во второй вкладке — вставить этот код в «Присоединиться по коду», нажать
   «Войти».

**Вариант Б — матчмейкинг (случайный подбор):**
1. В обеих вкладках задать одинаковые настройки (размер поля/правила).
2. В обеих нажать «Искать соперника» — сервер сведёт их автоматически.

**Вариант В — против бота (одна вкладка):**
1. Отметить «Играть с ботом», выбрать уровень сложности, нажать «Создать
   комнату».
2. Партия начнётся сразу — бот сам отвечает на каждый ваш ход.

3. Играть — сервер синхронизирует ходы между вкладками в реальном времени.

Чтобы проверить переподключение вручную: пока партия идёт, в DevTools →
Network поставьте throttling «Offline» на 5–10 секунд, потом снова «Online»
(или просто отключите Wi-Fi ненадолго). Клиент сам восстановит соединение,
и партия продолжится с того же места — без потери хода или счёта.

## Сила бота: свободы групп и подбор весов по логам партий

Бот в этом шаге проигрывал почти все партии людям, регулярно давая себя
полностью окружить (счёт вида 30-40:0 в логах). Причина: оценочная функция
(`evaluateStatic` в `gameEngine.js`) знала только про territory/cohesion/
stones/захваты, но не про то, что связная группа живых камней постепенно
теряет пути наружу — этот сигнал появлялся только постфактум, в момент
самого захвата, что обычно за горизонтом поиска (3-5 полуходов).

Добавлен термин **liberty** (по аналогии со «свободами» в го):
`computeGroupLiberties()` считает для каждой связной группы живых камней,
сколько у неё осталось пустых соседних клеток. `evaluateStatic` штрафует
группы игрока с малым числом свобод и симметрично поощряет давление на
группы соперника с малым числом свобод — то есть теперь боту одинаково
выгодно и защищаться от окружения, и окружать самому. Этот же сигнал
используется в сортировке кандидатов (`quickScore`/`computeUrgentCells`),
чтобы срочный ход (спасти/добить группу в атари) не вылетал из top-N при
обрезке по `candidateCap`/`branchFactor` до того, как поиск успеет его
увидеть — раньше это и выглядело как «бот защищает обречённые точки».

Вес нового термина (как и остальные веса — `potential`/`cohesion`/`stones`)
больше не жёстко зашит в код на постоянной основе: `BOT_WEIGHTS` в
`gameEngine.js` — это только начальное значение. Реальные «боевые» веса
хранятся в таблице `bot_weights` (см. `db.js`/`gamelog.js`) и подбираются
офлайн-скриптом:

```bash
node tools/train-bot.js --difficulty strong --generations 8 --population 6 --games 12
```

Скрипт — это self-play (1+λ)-эволюционная стратегия: движок играет сам с
собой разными наборами весов на быстрых настройках `Engine.TRAIN_DIFF`,
побеждающий вариант становится новым эталоном. Стартовые позиции self-play
партий берутся не с пустой доски, а из первых ходов реально доигранных
партий в БД (`gameLog.getFinishedGamesForTraining()`) — так подбор весов
оценивается в позициях, которые реально возникают в игре с людьми, а не
только в «удобных» для бота дебютах. `server.js` читает текущие веса из
`bot_weights` при каждом ходе бота (`botWeightsFor()`) — новое поколение
весов подхватывается сразу, без передеплоя.

Это не нейросеть и не behavior cloning по ходам людей — у эвристического
альфа-бета бота попросту нет параметров такого рода. Если в будущем
понадобится буквально «имитировать стиль игры человека» (а не просто
побеждать), это отдельная задача — обучаемая модель поверх записанных
ходов (`moves`), а не тюнинг 4 весов существующей эвристики.

## Что дальше

Девять шагов из плана реализованы: общий движок правил, минимальный
сервер, комнаты по коду, матчмейкинг, переподключение, игра с ботом,
регистрация/вход, ник вместо «Индиго»/«Гранат», логи партий и статистика.
Дальше — уже не «прототип», а вопросы боевой эксплуатации: настоящий
деплой (Render/Fly.io/PartyKit — обсуждали раньше; для Render важно, что
`data/tochki.db` переживёт рестарт только на **персистентном диске**, на
бесплатном тарифе с эфемерной файловой системой файл слетит при каждом
деплое/засыпании — тогда либо платный disk, либо переезд на managed
Postgres — а с ним пропадёт не только регистрация, но и весь накопленный
лог партий), вынос расчёта бота в worker_threads (см. «Известное
ограничение» выше), персистентное хранилище самого СОСТОЯНИЯ активных
комнат (сокеты/таймеры реконнекта по-прежнему только в памяти — рестарт
сервера обрывает партии в процессе, хотя их лог в БД уже сохранён и не
пропадёт), UI для просмотра истории/статистики в самом клиенте (сейчас
это только HTTP API — `client.html` его не вызывает и ничего не
